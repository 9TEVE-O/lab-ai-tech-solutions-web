## Interactive AI visual system — nodes, movement and evidence graphics

The current website instruction authorises an interactive AI visual direction in principle. The non-adopted Visual Evidence Grammar may support this work but does not itself authorise implementation.

The website should feel contemporary and technically alive, but interaction must clarify the workflow rather than simulate intelligence.

### Approved visual families

Use original LAB visual components derived from the current evidence and workflow direction:

- **Reasoning Map nodes and edges** — source, evidence, interpretation, review, approval, blocked state and output;
- **source-to-structure-to-review-to-outcome paths** — show where information moves and where authority changes;
- **knowledge-system constellations** — sparse, labelled node groups that explain relationships rather than decorative network density;
- **document-intelligence paths** — document card, extraction/classification node, review state, approval gate and traceable output;
- **workflow / agent blocks** — modular tool or agent actions with visible human boundaries and explicit status;
- **approval-state transitions** — a gate opens only after a visible approval action in the illustration;
- **source-trace expansion** — visitors may expand a trace to inspect the relationship between a source, decision and output;
- **failure and rollback states** — warnings, blocked paths and recovery routes should be visually representable.

Do not use these visuals as proof of deployed capability. Illustrative and synthetic graphics must be labelled where necessary.

### Movable-part rules

Movable parts are allowed where interaction improves understanding.

Preferred interactions:

- select a node to reveal its role, source state, limitation or approval state;
- expand or collapse a source trace;
- move between workflow states using explicit controls;
- drag a node only when spatial exploration is useful, with a keyboard and tap/click equivalent;
- reposition or focus a diagram in response to user input;
- animate an edge only when a relationship or state change has actually been selected or demonstrated;
- reveal blocked, rollback or approval paths on demand.

Do not implement:

- perpetual floating nodes;
- ambient particle systems;
- fake neural-network activity;
- decorative spinning;
- motion that implies processing when no process is occurring;
- animated connections that imply causality, certainty or proof;
- drag-only essential information;
- hover-only content;
- motion that delays access to copy, limitations or calls to action.

### Interaction implementation defaults

Use the lightest maintainable implementation:

1. semantic HTML + CSS for state transitions and simple movement;
2. responsive inline SVG for node/edge diagrams;
3. React state for interaction;
4. no WebGL, WebGPU, Three.js, physics engine or canvas dependency unless a documented prototype proves that SVG/CSS cannot meet the requirement.

All essential meaning must remain available as normal DOM text.

Motion should normally use `transform` and `opacity`, avoid layout thrashing, and stop when the component is not active or visible.

### Reduced-motion and static-equivalent requirement

Every interactive visual must provide:

- `prefers-reduced-motion` behaviour;
- a static equivalent containing the same essential meaning;
- keyboard-complete controls;
- visible focus;
- touch targets of at least 44 by 44 CSS pixels;
- no essential information encoded only through movement, colour or position.

If reduced motion is requested, continuous or transitional movement must collapse to immediate state changes.

### Website-specific Rubric OS profile

For this frozen website build, the thresholds and weights written below are the controlling **website-specific Rubric OS profile**.

The upstream Rubric OS source retrieved during preparation was not available under a stable canonical repository filename. Therefore:

- do not present the upstream file as canonical solely from its storage location;
- do not change the values below by silently substituting a different rubric source;
- any later rubric revision must be recorded as a controlled amendment to this pack or a successor version.

The six review domains are:

1. **Security** — weight 25%;
2. **Bugs and Correctness** — weight 25%;
3. **Performance** — weight 20%;
4. **DRY / SOLID / maintainability** — weight 15%;
5. **UX / Accessibility** — weight 10%;
6. **Design System integrity** — weight 5%.

Known production-stage minimums from the current Rubric OS source:

- Security: **4/5 minimum**;
- Bugs and Correctness: **4/5 minimum**;
- Performance: **4/5 minimum**;
- Design System: **3/5 minimum**.

Do not invent missing canonical thresholds for DRY/SOLID or UX/A11y. Until those thresholds are explicitly confirmed, both domains require a scored rationale and **no unresolved critical finding**.

### Automation-cliff rule

Do not waste the Rubric OS by repeating only what linters already catch.

Automated checks should cover the lower layer:

- dependency and known-vulnerability scanning;
- secret scanning;
- lint and type/static checks where configured;
- broken links;
- bundle size and basic Core Web Vitals;
- token/raw-value checks;
- automated accessibility checks;
- build and route smoke tests.

The Rubric OS must also inspect the higher layer that requires engineering judgement:

- security or privacy bypass through business logic;
- unsafe use of AI-generated or user-supplied content;
- race conditions, impossible states and stale state;
- long interaction tasks and INP regressions;
- abstractions that add more complexity than they remove;
- dead or parallel architectures that create source-of-truth ambiguity;
- component prop explosion and duplicated interaction logic;
- visual-system drift from approved tokens and component rules;
- cognitive accessibility and keyboard/screen-reader behaviour;
- node graphs or motion that imply proof, certainty, processing or approval without evidence;
- hidden failure, rollback or blocked states.

### Finding record

Each Rubric OS finding must record:

- finding ID;
- domain;
- score or severity;
- affected route/component/file;
- evidence;
- whether automated or judgement-based;
- failure mode;
- user/business impact;
- smallest corrective action;
- retest method;
- release-blocking status;
- owner;
- final disposition.

### Rubric stop conditions

Return `HOLD — NOT READY FOR PUBLIC RELEASE` when any of the following applies:

- Security score below 4;
- Bugs and Correctness score below 4;
- Performance score below 4;
- Design System score below 3;
- unresolved critical UX/A11y finding;
- unresolved critical DRY/SOLID or maintainability finding;
- dead or parallel runtime architecture can still influence the production build;
- stale offer or parked generator remains publicly reachable;
- enquiry path is non-functional or collects data outside the approved boundary;
- interactive visual is inaccessible by keyboard or lacks a static/reduced-motion equivalent;
- motion implies processing, intelligence, approval, causality or proof that is not actually present;
- node interaction introduces material INP, layout-shift or mobile-overflow failure;
- a score is asserted without test evidence.

Do not optimise for a perfect 5/5 in every category when it would add unjustified complexity. The Rubric OS is a contextual decision gate, not an over-engineering target.
